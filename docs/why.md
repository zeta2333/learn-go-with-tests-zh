# 为什么写单元测试，以及如何让它们为你所用

## 软件

软件的承诺在于它可以改变。它之所以叫*软*件，正是因为相比硬件，它是可塑的。一支优秀的工程团队理应是一家公司的宝贵资产：他们写出的系统能随业务一同演进，持续创造价值。

可为什么我们偏偏这么不擅长把它做好呢？彻底失败的项目你听过多少？或者沦为"遗留系统"（legacy），不得不整个推倒重写（而重写往往也照样失败！）

话说回来，软件系统到底是怎么"失败"的？它不是可以一直改、改到正确为止吗？说好的承诺呢！

很多人正在选择用 Go 来构建系统，因为它做了一系列设计取舍，人们希望这些取舍能让代码不容易沦为遗留系统。

- 我以前写 Scala，还专门[写过它是如何给你一根足够上吊的绳子的](http://www.quii.dev/Scala_-_Just_enough_rope_to_hang_yourself)。相比之下，Go 只有 25 个关键字，*很多*系统只用标准库加另外几个小库就能搭起来。理想状态是：用 Go 写的代码，过 6 个月回来看，依然看得懂。
- 在测试、基准测试、linter（代码静态检查工具）和发布交付方面，Go 的工具链相比大多数同类语言都堪称一流。
- 标准库非常出色。
- 编译非常快，足以支撑紧凑的反馈循环。
- Go 的向后兼容承诺。看起来 Go 未来会加入泛型和其他特性，但设计者们承诺过：哪怕是你 5 年前写的 Go 代码，也照样能编译。而我自己就实打实地花过好几个星期，把一个项目从 Scala 2.8 升级到 2.10。

即便有这么多优点，我们依然能把系统做得很糟糕。所以我们应该回望过去，理解软件工程里那些被反复验证的教训——无论你的语言多么光鲜（或者不那么光鲜），它们都适用。

1974 年，一位名叫 [Manny Lehman](https://en.wikipedia.org/wiki/Manny_Lehman_%28computer_scientist%29)（曼尼·莱曼）的聪明软件工程师提出了 [Lehman 软件演化定律](https://en.wikipedia.org/wiki/Lehman%27s_laws_of_software_evolution)（Lehman's laws of software evolution）。

> 这些定律描述的是一种平衡：一边是推动新开发的力量，另一边是拖慢前进的力量。

如果我们还想有希望摆脱那个无休止的循环——上线一个系统，眼看着它变成遗留系统，然后再一遍又一遍地重写——那这两股力量就非理解不可。

## 持续变化定律

> 任何在真实世界中被使用的软件系统，都必须不断变化，否则它在所处环境中会变得越来越没用

系统*必须*变化，否则就会变得越来越没用——这道理听起来显而易见，可它被无视的频率有多高？

很多团队受到的激励是：在指定日期交付项目，然后奔向下一个项目。如果软件"走运"，至少还有个像样的交接，把它移交给另一拨人维护——当然，那拨人并不是当初写它的人。

人们经常操心的是挑一个能帮自己"快速交付"的框架，却不关心系统能不能长寿——也就是它日后需要如何演进。

哪怕你是位了不起的软件工程师，也照样逃不过"预知不了系统的未来需求"这条坎。业务一变，你当年写的某些漂亮代码，如今就派不上用场了。

Lehman 在 70 年代手感火热，又给我们送来一条值得细品的定律。

## 复杂度递增定律

> 系统在演进的过程中，复杂度会不断上升，除非刻意下功夫去降低它

他的意思是：软件团队不能当闭着眼睛的"功能工厂"，只顾往软件上堆越来越多的功能，还指望它能在长跑中活下来。

随着领域知识的演进，我们**必须**持续管理系统的复杂度。

## 重构

软件工程里能让软件保持可塑的方面有很多，比如：

- 开发者的自主权
- 总体上"好"的代码：合理的关注点分离，等等等等
- 沟通能力
- 架构
- 可观测性
- 可部署性
- 自动化测试
- 反馈循环

这里我想单聊重构。这个词已经被用滥了——"我们需要重构一下这里"，这话可以对一个第一天开始编程的开发者脱口而出，连想都不用想。

这个说法到底从哪儿来？重构和普普通通写代码的区别又在哪里？

我知道，我和很多其他人都*以为*自己在做重构，其实我们搞错了

[Martin Fowler 描述过人们是怎么把它用错的](https://martinfowler.com/bliki/RefactoringMalapropism.html)

> 然而，"重构"这个词经常被用在不合适的场合。如果有人说他们的系统因为重构瘫了好几天，那你基本可以断定：他们做的不是重构。

那它到底是什么？

### 因式分解

在学校学数学时，你大概率学过因式分解。来看一个非常简单的例子

计算 `1/2 + 1/4`

做法是先对分母做*因式分解*，把式子变成

`2/4 + 1/4`，接着就能得出 `3/4`。

我们能从这件事里学到几个要点。当我们*对式子做分解*时，我们**没有改变式子的含义**。两个式子都等于 `3/4`，但我们让它更好处理了：把 `1/2` 改成 `2/4`，它就更容易落进我们的"领域"里。

重构代码时，你是在想办法让代码更容易理解，让它更"贴合"你对系统该做什么的当前理解。关键在于：**你不应该改变行为**。

#### 一个 Go 例子

    func Hello(name, language string) string {
    
      if language == "es" {
         return "Hola, " + name
      }
    
      if language == "fr" {
         return "Bonjour, " + name
      }
      
      // imagine dozens more languages
    
      return "Hello, " + name
    }

几十个 `if` 语句排在一起怎么看怎么不舒服，而且"特定语言的问候语 + `, ` + `name`"这段拼接逻辑还写重复了。所以我要重构这段代码。

    func Hello(name, language string) string {
      	return fmt.Sprintf(
      		"%s, %s",
      		greeting(language),
      		name,
      	)
    }
    
    var greetings = map[string]string {
      "es": "Hola",
      "fr": "Bonjour",
      //etc..
    }
    
    func greeting(language string) string {
      greeting, exists := greetings[language]
      
      if exists {
         return greeting
      }
      
      return "Hello"
    }

这次重构具体用了什么手法其实不重要，重要的是：我没有改变行为。

重构的时候你想怎么折腾都行：加接口、加新类型、加函数、加方法，等等。唯一的规矩是不能改变行为

### 重构代码时，绝不能改变行为

这一点非常重要。一边重构一边改行为，等于同时在干*两*件事。作为软件工程师，我们学会了把系统拆成不同的文件/包/函数等等，因为我们知道，想一口气理解一大坨东西是很难的。

我们不想被迫同时惦记一大堆事，因为出错恰恰出在这种时候。我亲眼见过太多重构半途而废，就因为开发者贪多嚼不烂。

当年在数学课上用纸笔做因式分解，我只能靠脑子手动检查自己没有改变式子的含义。那么写代码做重构时，我们怎么知道自己没有改变行为？尤其是在一个不那么简单的系统上？

选择不写测试的人，通常只能依赖手工测试。除了小项目，这对其他任何东西都是个巨大的时间黑洞，长期来看根本撑不住。

**要想安全地重构，你需要单元测试**，因为它们能给你

- 信心：你可以放心重塑代码，不必担心改变行为
- 一份给人看的文档：说明系统应该有怎样的行为
- 比手工测试快得多、可靠得多的反馈

#### 一个 Go 例子

给 `Hello` 函数写的单元测试大概长这样

    func TestHello(t *testing.T) {
      got := Hello(“Chris”, es)
      want := "Hola, Chris"
    
      if got != want {
         t.Errorf("got %q want %q", got, want)
      }
    }

在命令行里跑一下 `go test`，就能立刻知道我的重构有没有偷偷改变行为。实际工作中，最好摸清编辑器/IDE 里那个一键跑测试的"魔法按钮"。

你要让自己进入这样一种循环：

- 小幅重构
- 跑测试
- 再来

整个过程始终处在一个非常紧凑的反馈循环里，这样你才不会一头扎进兔子洞越陷越深，犯下错误。

如果一个项目里所有关键行为都有单元测试护体，反馈又远在一秒之内就能到手，那它就是一张给你底气的安全网，让你在需要时敢于大胆重构。这正好帮我们抵挡 Lehman 说的那股不断涌来的复杂度之力。

## 既然单元测试这么好，为什么还有人抗拒写它？

一边是有人（比如我）反复念叨：单元测试对系统的长期健康至关重要，因为它让你能一直放心地重构。

另一边则有人大倒苦水：单元测试实际上在*妨碍*重构。

问问你自己：重构的时候，你有多少次不得不连测试一起改？这些年我待过不少测试覆盖率很漂亮的项目，可工程师们还是不愿重构，因为光是想到要改测试就觉得费劲。

这跟我们被承诺的完全相反啊！

### 这是怎么回事？

想象一下，需求是实现一个正方形，而我们认定完成这件事的最佳方案是把两个三角形粘在一起。

![两个直角三角形拼成一个正方形](assets/triangles-square.jpg)

我们围着正方形写单元测试，确保四条边都相等；接着又围着三角形写了一些测试。为了确保三角形渲染正确，我们断言三个角加起来是 180 度，或许再检查一下确实拼了 2 个，等等等等。测试覆盖率这么重要，这些测试写起来又容易，何乐而不为？

几周后，持续变化定律找上门来，一位新开发者做了一些改动。她认为，正方形改用 2 个矩形来拼、而不是 2 个三角形，会更好。

![两个矩形拼成一个正方形](assets/rectangles-square.jpg)

她动手做这个重构，结果一堆测试挂掉，发来的信号乱成一团。她真的破坏了什么重要行为吗？现在她只能去翻这些三角形测试，努力搞清楚到底发生了什么。

*正方形是用三角形拼的还是别的什么，其实根本不重要*，可**我们的测试错误地抬高了实现细节的地位**。

## 优先测试行为，而不是实现细节

每当听到有人抱怨单元测试，问题往往出在测试站错了抽象层级：它们在测实现细节，对协作者（collaborator）过度 spy，mock 满天飞。

我认为这源于两件事：对"单元测试是什么"的误解，以及对虚荣指标（测试覆盖率）的追逐。

如果我说只测行为，那是不是干脆只写系统/黑盒测试就好了？这类测试在验证关键用户路径上确实价值很大，但它们通常写起来费劲、跑起来慢。正因如此，它们对*重构*帮助不大——反馈循环太慢了。另外，跟单元测试比，黑盒测试也不太擅长帮你定位根本原因。

那么，什么*才是*正确的抽象层级？

## 写好单元测试是个设计问题

先把测试放一边。理想情况下，你的系统里应该有一些自包含、解耦的"单元"，各自围绕领域中的关键概念建立。

我喜欢把这些单元想象成一块块简单的乐高积木：它们有内聚一致的 API，可以跟其他积木拼出更大的系统。在这些 API 底下，可能有几十个东西（类型、函数等等）在协同工作，让它们按需运转。

比方说，用 Go 写一个银行系统，你可能会有一个 "account" 包。它对外呈现的 API 不泄漏实现细节，而且容易集成。

如果你拥有这些具备上述性质的单元，就可以针对它们的公开 API 写单元测试。*按定义*，这些测试测到的只可能是有用的行为。而在这些单元底下，我可以随心所欲地按需重构实现，测试在绝大多数情况下不会来捣乱。

### 这些算单元测试吗？

**算**。单元测试针对的就是我描述的那种"单元"。它*从来*不是指只能针对单个类/函数/随便什么东西来测。

## 把这些概念串起来

我们已经聊了

- 重构
- 单元测试
- 单元设计

我们开始能看出：软件设计的这几个侧面是互相成就的。

### 重构

- 为我们检验单元测试提供信号。如果重构之后还得靠手工检查，说明测试不够，要补。如果测试不该挂却挂了，说明测试站错了抽象层级（或者毫无价值，该删就删）。
- 帮我们处理单元内部以及单元之间的复杂度。

### 单元测试

- 为重构兜起一张安全网。
- 验证并记录单元的行为。

### （设计良好的）单元

- 容易写出*有意义*的单元测试。
- 容易重构。

那么，有没有一套流程，能帮我们到达这样一种境界：持续重构代码来管理复杂度，让系统始终保持可塑？

## 为什么要测试驱动开发（TDD）

有些人听了 Lehman 那句"软件必须变化"，可能会想过头：一门心思扑在精巧繁复的设计上，前期就投入大量时间想造出"完美"的可扩展系统，结果猜错了方向，哪儿也去不了。

这就是软件行业"美好的旧时光"：分析师团队花 6 个月写一份需求文档，架构师团队再花 6 个月搞出一个设计，几年之后整个项目宣告失败。

我嘴上说着"旧时光"，可这种事现在还在上演！

敏捷（Agile）教会我们要迭代地工作：从小处起步，让软件逐步演化，这样我们才能对软件的设计、以及它在真实用户面前的表现，快速拿到反馈；TDD 正是把这套做法落成了硬性纪律。

TDD 推崇的方法论就是：持续重构，迭代交付。它借此直面了 Lehman 讲的那些定律，以及历史上用惨痛代价换来的其他教训。

### 小步前进

- 为一小块想要的行为写一个小测试
- 确认测试失败，且错误信息清晰（红）
- 写最少的代码让测试通过（绿）
- 重构
- 重复

等你熟练之后，这种工作方式会变得又自然又快。

你会开始期待这个反馈循环不会太久，而当系统处于不"绿"的状态时，你反而会觉得不安——因为那可能说明你已经掉进兔子洞了。

你始终在推进小而有用的功能，背后稳稳垫着你测试给出的反馈。

## 总结

- 软件的力量在于我们可以改变它。*绝大多数*软件都会随时间以无法预料的方式需要改变；但别试图过度设计，因为未来实在太难预测。
- 我们要做的是让软件始终保持可塑。软件要演进，就必须不断重构，否则它只会变成一团乱麻
- 一套好的测试套件能帮你更快、更从容地重构
- 写好单元测试是个设计问题，所以认真考虑你的代码组织结构，让它拥有一个个有意义的单元，可以像乐高积木一样拼装整合。
- TDD 能帮你、也会逼着你以迭代的方式设计出分解良好的软件，背后有测试撑腰，未来的需求来了也不怕。
