# 反模式

隔一段时间，就有必要检视一下自己的 TDD 技巧，提醒自己哪些行为应当避免。

TDD 流程在概念上很简单，但真正做起来，你会发现它不断挑战你的设计功力。**别误以为是 TDD 难，难的是设计！**

本章列举了若干 TDD 与测试的反模式，以及相应的补救办法。

## 完全不做 TDD（Not doing TDD at all）

当然，不用 TDD 也能写出优秀的软件，但我见过的许多毛病——代码设计上的、测试质量上的——如果当初规规矩矩地按 TDD 来，还真是难折腾出来。

TDD 的一个强项，是给了你一套正式的流程去拆解问题：先弄明白你想达成什么（红），把它做出来（绿），再好好想想怎么把它做对（蓝/重构）。

没有这套流程，做法往往随意又松散，工程也_可能_因此变得比它_本可以_有的样子更难。

## 误解重构步骤的约束（Misunderstanding the constraints of the refactoring step）

我去过不少工作坊、群体编程（mobbing）或结对编程（pairing）的现场，有人刚让一个测试通过、正处在重构阶段。琢磨了一会儿，他觉得把一部分代码抽出去、装进一个新的结构体里会更好；这时一位初出茅庐的学究大喊：

> 你不能这么干！你得先为它写个测试，我们可是在做 TDD！

这似乎是个常见的误解。**测试转绿之后，代码随你怎么摆弄都行**，唯一不许做的是**增加或改变行为**。

这些测试的意义，就在于给你_重构的自由_，让你找到合适的抽象，让代码更容易修改、更容易理解。

## 永不失败的测试（evergreen tests）

这种事出现之频繁令人吃惊。你开始调试或修改一些测试，然后意识到：这个测试根本不存在会失败的场景。或者说，至少它不会以它_本该_防范的那种方式失败。

如果你照着 TDD 的**第一步**做，这种情况_几乎不可能_发生：

> 写一个测试，看它失败

写出这种测试的，几乎都是在代码_写完之后_才补测试的人，再或者，是在追逐测试覆盖率而不是在打造一套有用的测试套件的人。

## 无用的断言（Useless assertions）

你有没有过这种经历：在某个系统上改挂了一个测试，然后看到这么一条信息？

> `false was not equal to true`

我知道 false 不等于 true。这条消息毫无帮助，它没告诉我到底弄坏了什么。这正是没走 TDD 流程、也没读失败错误信息的典型症状。

回到起点重来：

> 写一个测试，看它失败（并且别让错误信息拿不出手）

## 断言无关细节（Asserting on irrelevant detail）

举个典型例子：对一个复杂对象整体做断言，而实际上这个测试在意的只是其中一个字段的值。

```go
// 别这样写，现在你的测试就跟整个对象紧密耦合了
if !cmp.Equal(complexObject, want) {
	t.Error("got %+v, want %+v", complexObject, want)
}

// 具体一点，把耦合放松
got := complexObject.fieldYouCareAboutForThisTest
if got != want {
	t.Error("got %q, want %q", got, want)
}
```

多余的断言不仅会在你的这份"文档"里制造噪音、让测试更难读，还会无谓地把测试跟它并不关心的数据耦合在一起。这意味着，一旦你碰巧改了对象的字段，或是改变了它们的行为，就可能遭遇意料之外的编译问题或测试失败。

这就是"红"阶段执行得不够严格的一个例子。

- 让现有的设计牵着测试的写法走，**而不是去想期望的行为**
- 对失败测试的错误信息没有给足考量

## 单个场景中堆砌大量断言（单元测试）

断言一多，测试就难读，失败了也不好排查。

它们往往是悄悄渗进来的：尤其是当测试的准备工作很繁琐时，你会不愿意把同样可怕的准备代码再复制一份，去断言别的东西。与其如此，你应该去修设计上的毛病——正是它们让断言新东西变得困难。

一条好用的经验法则：争取每个测试只做一次断言。在 Go 里，遇到确实需要多次断言的场合，可以利用子测试把它们清晰地划分开。这也是个顺手的好办法，用来把针对行为的断言和针对实现细节的断言分开。

至于准备或执行时间本身就是约束的那类测试（比如驱动一个网页浏览器的验收测试），你就得权衡一下：调试起来稍显费劲，换来的是测试执行时间，值不值。

## 不倾听你的测试（Not listening to your tests）

[Dave Farley 在他的视频《When TDD goes wrong》里指出](https://www.youtube.com/watch?v=UWtEVKVPBQ0&feature=youtu.be)：

> TDD 能为你的设计提供最快的反馈

就我自己的经验，很多开发者嘴上在做 TDD，却经常无视 TDD 流程反馈回来的信号。结果他们还是被脆弱又烦人的系统困住，手边还跟着一套蹩脚的测试套件。

简单说，如果你的代码难测试，那_使用_你的代码也一样难受。把你的测试当成代码的第一个用户，你的代码到底好不好相处，一试便知。

这一点我在全书里强调过很多次，这里再说一遍：**倾听你的测试**。

### 准备代码过长、测试替身过多，诸如此类（Excessive setup, too many test doubles, etc.）

你有没有见过这样的测试：正戏还没开场，光准备代码就有 20 行、50 行、100 行、200 行？之后每次要改代码、重返这片烂摊子时，你是不是开始憧憬另一种职业生涯了？

这里有什么信号？_听_，复杂的测试 `==` 复杂的代码。你的代码为什么复杂？它非复杂不可吗？

- 测试里塞满测试替身，说明被测代码有大量依赖——也就是说，你的设计需要下功夫了。
- 如果你的测试依赖设置各种与 mock 的交互，说明你的代码在跟它的依赖大量交互。问问自己，这些交互能不能更简单些。

#### 泄漏的接口（leaky interfaces）

如果你声明了一个方法多多的 `interface`，那就指向了一个泄漏的抽象。想想怎么用一组更精炼的方法——理想情况就一个——来定义这层协作。

#### 接口污染（interface pollution）

正如一句 Go 谚语所说：*接口越大，抽象越弱*。如果你给包的使用者暴露一个巨大的接口，就等于逼他们在自己的测试里写出一个匹配整个 API 的 stub/mock，连用不到的方法也得实现（有时干脆 panic 一下，表明这些方法不该被调用）。这种反模式叫做[接口污染](https://rakyll.org/interface-pollution/)，标准库只提供一个个小小的接口，原因正在于此。

正确的做法是，从包里暴露一个朴素的结构体，把相关的方法全部导出；至于声明自己的接口、抽象出他们需要的那部分方法，这份自由留给 API 的使用者：比如 [go-redis](https://github.com/redis/go-redis) 交给 API 客户端的就是一个结构体（`redis.Client`）。

一般来说，只有满足下列条件时才应该向使用者暴露接口：

- 接口由一小撮内聚的函数组成。
- 接口和它的实现需要解耦（比如使用者要在多个实现之间挑选，或者他们需要 mock 掉一个外部依赖）。

#### 想清楚你用的是哪类测试替身（Think about the types of test doubles you use）

- mock 有时确实有用，但它威力太大，因此也容易被滥用。不妨给自己立个约束：改用 stub。
- 用 spy 验证实现细节有时也有用，但要尽量避开。记住，你的实现细节通常并不重要，能不让测试耦合它们就别耦合。要让你的测试耦合**有用的行为，而不是附带的细节**。
- 如果测试替身的分类还让你有点犯迷糊，可以[读读我谈测试替身命名的文章](https://quii.dev/Start_naming_your_test_doubles_correctly)

#### 合并依赖（Consolidate dependencies）

下面这段代码是一个 `http.HandlerFunc`，负责处理网站的新用户注册。

```go
type User struct {
	// 一些用户字段
}

type UserStore interface {
	CheckEmailExists(email string) (bool, error)
	StoreUser(newUser User) error
}

type Emailer interface {
	SendEmail(to User, body string, subject string) error
}

func NewRegistrationHandler(userStore UserStore, emailer Emailer) http.HandlerFunc {
	return func(writer http.ResponseWriter, request *http.Request) {
		// 从请求体里取出用户（处理错误）
		// 检查用户是否已存在（处理重复、错误）
		// 存储用户（处理错误）
		// 撰写并发送确认邮件（处理错误）
		// 走到这里，就返回 2xx 响应
	}
}
```

乍一看，说这个设计还不算糟似乎也合理：它才 2 个依赖嘛！

不妨从处理器的职责出发，重新评估一下这个设计：

- 把请求体解析成一个 `User` ✅
- 用 `UserStore` 检查用户是否已存在 ❓
- 用 `UserStore` 存储用户 ❓
- 撰写一封邮件 ❓
- 用 `Emailer` 发送邮件 ❓
- 视成功、出错等情况，返回合适的 http 响应 ✅

要测这段代码，你就得写一大堆测试，还得给它们配上各式各样的测试替身、spy，等等。

- 需求要是扩张了呢？邮件要多语言版本？还要再发一条短信确认？为了这种变更你得去改一个 HTTP 处理器，你觉得说得过去吗？
- "我们应该发一封邮件"这么重要的一条规则，居然住在 HTTP 处理器里，你感觉对劲吗？
    - 为了验证这条规则，你还得走一遍造 HTTP 请求、读响应的全套仪式，何苦呢？

**倾听你的测试**。以 TDD 的方式为这段代码写测试，应该很快就会让你浑身不对劲（至少，也会惹恼你内心那个懒惰的开发者）。要是觉得痛苦，停下来想想。

要是设计换成这样呢？

```go
type UserService interface {
	Register(newUser User) error
}

func NewRegistrationHandler(userService UserService) http.HandlerFunc {
	return func(writer http.ResponseWriter, request *http.Request) {
		// 解析用户
		// 注册用户
		// 处理错误，发送响应
	}
}
```

- 处理器很好测 ✅
- 注册规则的变更被隔离开来，不再牵扯 HTTP，测试起来也更简单 ✅

## 破坏封装（Violating encapsulation）

封装非常重要。我们之所以不把包里的所有东西都导出（或者叫 public），是有原因的：我们想要内聚且表面积小的 API，避免紧耦合。

有时人们会忍不住为了让某个东西可测，把一个函数或方法设成公开。这么做会让你的设计变糟，还会给代码的维护者和使用者发出混乱的信号。

后果之一可能是：开发者费劲调试一个测试，最后才发现被测的那个函数_只在测试里被调用过_。这显然是**糟糕透顶的结果，纯属浪费时间**。

在 Go 里，写测试时不妨默认抱着_包使用者的视角_。你可以把这变成一条编译期的硬约束：把测试放进一个测试包，比如 `package gocoin_test`。这样你只能访问包里导出的成员，想耦合实现细节也耦合不上。

## 变复杂的表驱动测试（Complicated table tests）

当各个场景的测试准备都一样、只是想换换输入时，表驱动测试是同时覆盖大量场景的好办法。

_但是_，一旦你硬要把其他类型的测试塞进同一张"辉煌"的大表里，它们就会读起来费劲、理解起来费劲。

```go
cases := []struct {
	X                int
	Y                int
	Z                int
	err              error
	IsFullMoon       bool
	IsLeapYear       bool
	AtWarWithEurasia bool
}{}
```

**别怕跳出你的表格，另写新的测试**，而不是往表格的 `struct` 里添新字段、新布尔值。

写软件时有一条要记在心里：

> [简单不等于容易](https://www.infoq.com/presentations/Simple-Made-Easy/)

往表格里"顺手"加一个字段也许很容易，但它可能让事情离"简单"越来越远。

## 总结（Summary）

单元测试的大多数问题，通常都能追溯到：

- 开发者没有遵循 TDD 流程
- 设计糟糕

所以，去学习优秀的软件设计吧！

好消息是，TDD 能帮你_提升设计功力_，原因正如开头所说：

**TDD 的主要目的，就是为你的设计提供反馈。**第一百万次强调：倾听你的测试，它们就是你设计的镜子。

坦诚面对你的测试质量，认真听取它们给你的反馈，你也会因此成为更好的开发者。
